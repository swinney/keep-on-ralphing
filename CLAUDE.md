# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

`keep-on-ralphing` is **the Ralph loop harness itself** — a reusable kit for driving an
LLM coding agent through a task list one turn at a time, in a sandbox container, using
the **commit graph as the objective progress signal**. This repo is *not* a consumer
project; it is the thing other projects install. Keep that distinction front of mind:
the `/ralph-init`, `/ralph-status`, and `/ralph-build-base` skills act on a *target* repo
(or, for `/ralph-build-base`, the installed plugin's own bundled `base/`), never on this one.

Scope is deliberately narrow: **Linux + podman, single architecture, team-shared via
GitHub.** Not multi-arch, not macOS/Windows, not Docker-tested.

## Commands

```sh
make build-base   # build the ralph-base:v1 sandbox image from base/Containerfile (registry-free, UID/GID matched to you)
make test         # full kit suite: until_reset.py unit tests + ralph.sh behavioural scaffold (== bash base/tests/run.sh)
```

Run a single slice of the suite directly:

```sh
pytest -q -c base/tests/pytest.ini base/tests/test_until_reset.py   # unit tests only
bash base/tests/test_ralph_runner.sh                                # runner scaffold only
bash base/tests/test_gate_hook.sh                                   # gate-hook enforcement only
bash base/tests/test_review_gate.sh                                 # outer-loop review gate only
```

The test suite is self-contained — it needs only bash, git, python3 (+ pytest), and
`timeout`. `test_ralph_runner.sh` stubs the `claude` binary and drives `ralph.sh` against
git fixtures, so it runs without a container or real agent. `pytest.ini` is passed with
`-c` specifically to isolate from any surrounding project's pytest config.

CI (`.github/workflows/ci.yml`) runs exactly `make test` on Python 3.12 (matching the
base image) and **does not build the podman image** — because the suite stubs `claude` and
uses git fixtures, it needs no container. So a green local `make test` is a faithful
predictor of green CI.

## Architecture: the three-channel split

The kit is organized by **where each piece runs**, not by file type. Internalize this:

| Channel | Lives in | What it is |
|---|---|---|
| **In-container** | `base/` | The base podman image. Bakes `ralph.sh` + `until_reset.py` onto PATH. |
| **Host-side** | `skills/` | The Claude Code plugin: `/ralph-init` (scaffold), `/ralph-status` (report), `/ralph-build-base` (build `ralph-base:v1` from the plugin's bundled `base/`, clone-free). |
| **In-repo (data)** | generated by `/ralph-init` from `templates/` | `ralph.conf`, `PROMPT.md`, `tasks.md`, thin `Containerfile`/`Makefile`, the enforced gate (`scripts/gate.sh` + `hooks/pre-commit` + CI), and the `specs/tests/decisions` skeleton with seeded `STATUS.md`/`questions.md`. |

The load-bearing rule that ties these together: **the loop machinery has exactly one
source — the base image.** A consumer project's `Containerfile` is just
`FROM ralph-base:v1` plus its own toolchain; it carries *no* `scripts/`. When editing the
runner, edit `base/scripts/` only — never reintroduce vendored copies into templates or
the example. (`/ralph-init` is explicitly forbidden from writing `ralph.sh`/`until_reset.py`
into a target repo.)

One deliberate exception to "consumers carry no `scripts/`": `/ralph-init` scaffolds
`scripts/gate.sh` into a consumer. That rule targets the loop *runner*; the gate command
is project-*owned* config (this project's own formatter/linter/types/tests), analogous to
`ralph.conf`, so it legitimately lives in the consumer. It is the single source the
pre-commit hook (`hooks/pre-commit`, installed via `core.hooksPath` by the Makefile
`hooks` target) and the CI workflow both call — a red gate blocks the commit, so a red
turn makes no commit and the loop stalls. `base/tests/test_gate_hook.sh` verifies that.
`core.hooksPath` is repo-wide (it lives in the shared `.git/config`), so once set the
gate applies to every commit, host or container; the gate is meant to run in the
container where the toolchain lives. The specs dir is seeded with a spec-*writing guide*
(`specs/README.md`), never a placeholder spec — the loop builds to anything that looks
like a spec, so a fake one is worse than none.

`templates/` holds the per-project config surface (`*.template`, `ralph.conf.example`);
`example/` is a fully-resolved sample ("Acme Widgets") that doubles as the golden
reference for what `/ralph-init` should produce. `extras/` is explicitly **unsupported**
(experimental fan-out scripts) — not wired into the image, plugin, or tests.

**Skill interaction convention:** whenever a skill presents the operator a choice, it marks
one option "(recommended)" first with a one-line, repo-specific reason; high-stakes choices
(gate command, coverage threshold/mode, auto-merge) state the risk and still require
confirmation. This is presentation only — it never changes the actual defaults.

## This repo dogfoods what it ships — mind the namespace collision

The kit *generates* specs, a gate, CI, and decision records for consumers; this repo
*also runs its own* versions of those same artifacts for its own development. They are
different layers and must not be conflated:

| Artifact | This repo's own (edit for *this* repo) | What the kit emits (lives in `templates/`/`example/`) |
|---|---|---|
| Specs | `openspec/specs/`, `openspec/changes/` (OpenSpec workflow) | the `specs/README.md` writing-guide skeleton |
| CI | `.github/workflows/ci.yml` (runs `make test`) | `templates/ci.yml.template` |
| Decisions | `docs/decisions/` (ADRs, e.g. `0001-base-image-python-slim.md`) | the seeded `decisions/` skeleton |
| Gate | none — this repo's gate *is* `make test` | `templates/gate.sh.template` |

When a request says "update the spec" / "fix CI" / "add a decision," determine which
layer is meant: a change to *how the harness behaves* edits the `templates/`+`example/`
side (and usually a test); a change to *how this repo is built/verified* edits the
`openspec/`, `.github/`, `docs/decisions/` side. ADRs in `docs/decisions/` record *why*
the harness is the way it is — read the relevant one before reversing a baked-in choice
(image base, runtime portability, gate model).

## Releasing — two channels, unlinked versions

A release ships through **two independent channels that have no shared version**, and
nothing forces them to move together. Skipping either half ships a silent partial release:

- **Plugin** (`skills/` + `templates/`) — versioned by `.claude-plugin/plugin.json`. The
  Claude Code marketplace updater keys off this string. **Pushing commits without bumping
  the version makes `/plugin update` a no-op** — the new skill/templates never reach
  installs. The Skill tool also loads the *cached* plugin
  (`~/.claude/plugins/cache/.../<version>/`), **not** the working tree, so a skill change
  is invisible locally until the cache is refreshed.
- **Base image** (`base/`) — versioned by its tag (`ralph-base:v1`). Distributed by local
  `make build-base`, **not** the marketplace; a plugin update can't trigger it. Runner
  (`base/scripts/`) changes reach a machine only after a rebuild there.

**Checklist for any change that alters harness behaviour:**

1. `make test` green (faithful CI predictor — see Commands).
2. If `skills/` or `templates/` changed → **bump `.claude-plugin/plugin.json` version**
   (semver; this is what makes the plugin installable). Verify it's not still the old value.
3. Commit + push `main`.
4. If `base/scripts/` (the runner) or `base/Containerfile` changed → the base image must be
   rebuilt on every machine that runs the loop. The plugin bundles `base/` + the root
   `Makefile`, so a plugin user rebuilds clone-free via the `/ralph-build-base` skill
   (`make -C "$CLAUDE_PLUGIN_ROOT" build-base`); a contributor rebuilds from a checkout with
   `make build-base`. Because the runner ships *inside* the plugin, a `/plugin update` +
   rebuild keeps runner and plugin in lockstep — no second checkout to keep current. Bump the
   image tag if the change is breaking for existing consumers.
5. To apply on a machine: `/plugin marketplace update keep-on-ralphing` →
   `/plugin update ralph-harness@keep-on-ralphing`; confirm a `.../<new-version>/` dir
   appears in the cache.

A behaviour change usually touches BOTH channels (e.g. the review gate = runner logic in
`base/scripts/ralph.sh` *and* config keys in `templates/`), so steps 2 and 4 are commonly
both required in one release.

## How the loop works (base/scripts/ralph.sh)

- **One turn = one `claude -p --dangerously-skip-permissions <PROMPT.md`**, wrapped in
  `timeout`. The container boundary is what makes `--dangerously-skip-permissions`
  acceptable: the agent can do anything, but only to a bind-mounted workspace in a
  throwaway container.
- **Progress = commits.** A turn that changes `HEAD` made progress; a turn that doesn't is
  a *stall*.
- **Stop conditions (loop mode):** (1) a turn writes a *new* non-whitespace stop reason to
  `STATUS.md`; (2) `RALPH_MAX_STALLS` consecutive no-commit turns; (3) SIGINT.
- **Usage-limit pause is NOT a stall.** A rate-limited turn exits non-zero with a
  "hit your … limit · resets <time>" line; the loop greps that, calls `until_reset.py` to
  compute the sleep, waits, and **replays the same task** (decrementing the turn counter).
- **State** is written under `RALPH_STATE_DIR` (default `.ralph/`, gitignored):
  `current.json` (heartbeat), `status.jsonl` (one git-derived record per completed turn),
  `log/turn-<n>.txt` (line-buffered per-turn output), `turn` (counter). The
  `/ralph-status` skill reads these directly — there is no shipped status script.
- **Outer-loop review gate (`RALPH_REVIEW_GATE`, ON by default — the loop is
  GitHub-dependent).** After a committing turn, the *runner* (never the agent) pushes
  the branch, ensures a PR, requests an independent review (GitHub Copilot by default;
  `RALPH_REVIEWER` is the seam), and reads the verdict — PASS = **zero findings AND
  green CI** (CI read directly as ground truth). Findings are written to
  `review-findings.md`, which the PROMPT contract makes the agent's top-priority work
  next turn; persistent findings halt after `RALPH_REVIEW_MAX_ROUNDS` (the outer-loop
  analogue of `RALPH_MAX_STALLS`). Because it is on by default, **loop mode refuses to
  start without a git remote + authenticated `gh` + a non-base branch** — `/ralph-init`
  ensures these up front; `RALPH_REVIEW_GATE=0` is the explicit offline opt-out.
  `RALPH_AUTO_MERGE` (separate, default off) controls whether a PASSED PR merges or is
  parked for a human. **The load-bearing principle: the container agent stays
  GitHub-blind — all `git`/`gh` work is the runner's — so the gate is agent-agnostic
  and the verdict wait reuses the usage-limit pause (not a stall).** Note the subtlety:
  only the *agent* is GitHub-blind; the *runner* (`ralph.sh`) runs **in the container**
  and needs `gh` + auth there. So `gh` ships in `ralph-base` (the base image installs it,
  like `git`) and the consumer `Makefile` forwards a host-derived `GH_TOKEN`
  (`export GH_TOKEN ?= $(shell gh auth token)` + `-e GH_TOKEN`) — host login alone does
  not authenticate the in-container runner. `make test` stubs `gh` and CI does not build
  the image, so image contents are covered by `make smoke-base`, not the unit suite.

### Invariants to preserve when editing

- **`STATUS.md` change-detection is duplicated** between `ralph.sh` (snapshots
  `STATUS.md` at startup, stops only on a *changed* non-whitespace value) and the
  `ralph-status` skill (a blank/whitespace-only `STATUS.md` is NOT a stop). These two
  must stay in sync. `STATUS.md` is both the stop signal *and* the human cold-start
  breadcrumb, so it is normally non-empty when a fresh loop starts — that is why the
  comparison is against a startup snapshot, not against emptiness.
- **Config precedence is `environment > ralph.conf > built-in default`**, implemented by
  snapshotting `RALPH_*` env vars as re-runnable assignments and re-applying them *after*
  sourcing `ralph.conf`.
- **Deliberately old-runtime-compatible.** `ralph.sh` uses `printf %q` + `eval` (not
  associative arrays) so it runs on bash 3.2; `until_reset.py` defines its own `UTC` alias
  and targets Python 3.7+ (`datetime.UTC` is 3.11+). These look like mistakes but are
  intentional — see the "drift note" comment in `until_reset.py`. The base image runs
  3.12, but the runner is kept portable on purpose.

## The PROMPT.md contract (templates/PROMPT.md.template)

The prompt fed to the agent each turn enforces: one task per turn, a strict
spec → test → implement cycle, run the **full gate in CI order before every commit**
(format, don't just check), mark a task done only when its full cycle is green, and a
`Ralph-Task:` commit trailer with **no `Co-Authored-By`/AI attribution**. The gate
includes a **coverage threshold** — "tests pass" is not "the code is tested"; meet it by
testing the real path (exclude genuinely-untestable code via pragma or escalate, never
delete tests / lower the threshold). Coverage has two **modes**: a global floor (the
default, for greenfield) and patch/scoped coverage (recommended for brownfield, where a
global floor on existing untested code would fail the first commit) — `/ralph-init` always
offers both and recommends by greenfield/brownfield assessment. Coverage is a *supporting*
gate (it catches lazy tests, not faked-precondition tests — the review gate catches that
class, and also backstops scoped coverage's blind spot). When changing
the template, keep this contract intact and keep the `{{PLACEHOLDER}}` set closed (fill
every one, add none) — `/ralph-init` substitutes them. A wrong gate command (or
threshold) is the most damaging thing the scaffold can emit.
